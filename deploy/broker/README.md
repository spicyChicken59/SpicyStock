# Private broker connection

The checked-in GitHub Pages site is public research and manual execution tracking. It cannot safely hold brokerage credentials. This optional service serves the same dashboard and `/api` from one private HTTPS origin, so the user can connect an Alpaca account, review an exact order, confirm it, and refresh confirmed broker executions in the same UI. The browser receives an opaque secure session cookie; OAuth access tokens stay encrypted on the server.

The service is implemented and tested with offline broker doubles. It has not been deployed, connected to a real account, or used to place an order. Alpaca is the first supported adapter; an Alpaca **market-data API key is not an OAuth application or a brokerage connection**.

## Bring up a paper account

1. Register an Alpaca OAuth application with the exact redirect `https://YOUR-PRIVATE-HOST/api/oauth/callback`. Use Alpaca's application review process where required. The service requests only `trading data`; read-only account access is implicit. Credentials are supplied server-side when exchanging the authorization code.
2. Copy `deploy/broker/env.example` to `deploy/broker/bridge.env`. Set the exact HTTPS origin, client credentials, and a newly generated Fernet encryption key. Leave live trading disabled.
3. From the repository root run `docker compose -f deploy/broker/compose.yaml up -d --build`. Put a TLS reverse proxy on the same host in front of `127.0.0.1:8000`. The service binds only to localhost in this configuration. Preserve the original `Host` header. Do not log callback query strings, request/response bodies, cookies, or authorization headers in the proxy. Uvicorn access logging is disabled because callbacks contain temporary authorization codes.
4. Open that private origin and choose **Connect paper account**. Check `/api/status` for `configured: true` and, after OAuth, `state: paper`. Secure cookies require HTTPS, including local development. Sessions expire after eight hours; reconnecting recovers the same account's stored execution history.
5. Keep this private deployment's checked-in `docs/data.json` current with the successful evening scanner publication. Rebuild/redeploy from trusted main after publishing, or mount a read-only directory refreshed by your authenticated deployment process. The container does not fetch mutable snapshots or execute GitHub workflows itself. An old, missing, fixture, dry-run, degraded, or non-evening snapshot cannot authorize an order. Until the first real new-format scan publishes, trading is blocked with a specific explanation.
6. During the regular market session, use a current canonical 4% scan candidate to exercise **Preview → Confirm paper order → Refresh account → Confirmed execution**. Order acceptance is not recorded as a fill. Verify the stop's state at Alpaca, including a partial-fill scenario, before enabling live access.

Back up the named `broker-private` volume with SQLite's online backup facility, not by copying a live database without its WAL. Protect the encryption key separately. The SQLite database, WAL, and backups contain private account activity and must never be in the served `docs/` directory, Git, an Actions artifact, or the public site. Tokens are encrypted; fill/receipt metadata is private application data, not encrypted by this application. Use encrypted disks/backups and owner-only filesystem access. Run one private instance per owner. Optional multiuser hosting needs an operator authentication and tenancy review beyond this deployment.

## What is checked before an entry

The bridge owns the preview, quantity, mode, account binding, source snapshot hash, and unique order identity. It checks the broker's current clock and calendar (including holidays), a quote no older than 30 seconds, active/tradable US equity status, the app's trusted common-stock scope, the previous completed session's canonical 4% scan row, account trading permissions, cash, other pending orders, duplicate holdings/orders, spread, price distance, risk and notional ceilings. The checked-in stock list is a curated scope, not a claim that Alpaca's `us_equity` field distinguishes common stock from every ETF. By default, the bridge also accepts a current successful adaptive scan's classified members, verified against the server's snapshot session, selector version and membership identity. Client-provided tickers do not establish classification. Explicit BRIDGE_COMMON_STOCK_SYMBOLS or BRIDGE_COMMON_STOCK_FILE overrides remain restrictive and disable this extension. The bridge must receive the refreshed trusted snapshot; it does not fetch or trust browser state.

Only cash-funded whole-share long entries are supported. This version expects a stock account; unsupported non-stock symbols produce a clear account-scope error, and pending non-equity buys block entries because their cash requirements cannot be inferred from stock quantities. At most five symbols may be held or pending by default; a user may select a lower position cap. This cap includes existing holdings, pending buys and accepted order reservations, and is rechecked before submission. The user supplies entry, stop and risk percent. The service caps risk at 1% of current equity, a position at 25% of equity, and notional at $5,000 by default; these are configurable operator ceilings, not strategy recommendations or defaults inserted into a user's order. It reserves cash for pending buy limits and refuses uncertain pending market orders. Broker restrictions still determine whether an order can execute.

Each preview expires after 30 seconds. Confirming it rechecks market data, source, cash and risk. The sent order is a regular-hours GTC limit buy with an OTO protective stop. **The stop activates only after the entry fully fills; partial fills may be unprotected. Stops can execute below their stop price, do not trigger outside regular hours, and GTC entries remain active until canceled/expired.** Manage cancellations, changes, partial-fill protection and discretionary exits directly at the broker in this version; their later confirmed executions sync back here. Disconnecting the app does not cancel existing orders or broker-side authorization. Revoke the application in Alpaca's dashboard when appropriate.

Live access additionally requires `BRIDGE_LIVE_ENABLED=true`, an explicit `BRIDGE_LIVE_ACCOUNT_IDS` allowlist, and the connected account's entitled **real-time SIP** quote. There is no fallback from live SIP to delayed or IEX data. Paper uses IEX and labels its limited exchange coverage. No real order has been tested by this implementation task; complete the paper checks and operator setup before live use.

## Receipts, timeouts and execution history

An immutable preview is claimed under a SQLite transaction before any order POST. The service generates a stable `client_order_id`, sends at most one POST per preview, and records its outcome durably. A timeout or malformed receipt triggers a lookup by that same client ID. A missing lookup after a timeout is still uncertain; it does not permit a second POST. Browser retries only reconcile. The returned parent order must match the confirmed terms; an absent or mismatched protective stop retains the reconciliation lock and labels the protection unverified until a nested broker order lookup confirms it. An unresolved submission blocks further entries for that account, survives restart and reconnect, and is shown explicitly.

If an uncertain order never resolves, inspect the exact client order ID in the broker account and contact Alpaca if needed. There is intentionally no browser button that clears the lock or assumes a timeout means rejection. Restore the database from a consistent backup if it is corrupted; do not delete it to retry an uncertain order. The configured account identity and environment remain part of every reconciliation.

Only `FILL` activities become executions. Activities are deduplicated by broker ID within account and paper/live environment and cannot silently change after they have been saved. A correction under an existing ID produces a reconciliation error. Each refresh pages through at most 500 recent activities and retains them durably; at most 2,000 saved activities are returned to the UI. Truncation is explicit. This is an execution review window, not a complete broker statement, tax ledger, or fees-adjusted realized-P/L engine. Broker order statuses, positions, fills, paper simulations and manual journal entries remain separate.

## Operator verification

Install `requirements-dev.txt` (which includes the bridge and pytest) and run `python -m pytest tests/test_broker_bridge.py -q`. These tests use no network or brokerage account. They exercise OAuth state and cookie binding, encrypted persistence, exact-origin/CSRF enforcement, stale data and session guards, cash/risk/duplicate checks, preview expiry, server-owned order values, ambiguous POST reconciliation, persistence across restart, account isolation and fill identity conflicts. The root CI also runs the public UI and mocked private workflow checks. Actual OAuth registration, TLS, feed entitlements, broker availability, fill timing and stop activation must be verified on the operator's paper account.
